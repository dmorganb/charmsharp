# Phase 6.3.4e — Chare-template coverage audit

Status: 2026-10-29. Implementation baseline: Phase 6.3.4d (merged PR #54).
Target toolchain: Charm++ v8.0.0. This is a **bounded compatibility
assessment**, not a claim of general C++ template-language support.

## Executive assessment

**Phase 6.3 is complete for its agreed minimal scalar-chare template subset.**
The implementation declares, registers, and executes one-parameter scalar chare
templates, infers straightforward concrete proxy uses, and supports a separate
C++ translation unit using the generated shared template header. This has
executable coverage in the pinned Charm++ CI. It does **not** support arbitrary
template arguments, general inheritance, or whole-program specialization
discovery.

| Capability | Classification | Evidence / constraint |
| --- | --- | --- |
| `template<typename T> chare Worker` or `template<class T> chare Worker` | Implemented and runtime-tested | Exactly one type parameter; no defaults or packs; regular `.ci` template and `CBase_Worker<T>` generated |
| `template chare Worker<int>;` | Implemented and runtime-tested | Requires preceding scalar template declaration; emits concrete `chare Worker<int>;` in `<module>_specializations.ci`; not a C++ explicit instantiation |
| `CProxy_Worker<int>` auto-registration | Implemented and runtime-tested | Only recognized built-in concrete type spellings, only in the input `.csh`; inferred and explicit registrations deduplicated |
| Two concrete specializations of the same template | Runtime-tested | `Worker<int>` and `Worker<double>`; duplicate registration suppression |
| Multiple distinct template chares in one module | Runtime-tested | `First<int>` and `Second<double>`; definitions precede `CK_TEMPLATES_ONLY` in the generated header |
| Separate ordinary C++ consumer TU | Runtime-tested | Consumer includes `<module>_templates.h` and calls `CProxy_Worker<int>::ckNew`; explicit registration in the defining `.csh` remains necessary |
| Complex explicit specialization argument spellings | Parsed structurally, **not validated** | Parser captures balanced angle-bracket contents and rejects only the declared parameter name; acceptance does not prove Charmxi/PUP/C++ correctness |
| Ordinary or parallel inheritance on templated chares | **Deliberately rejected** | Phase 6.3.4d diagnostic; safe base-definition/header resolution and Charmxi inheritance semantics not implemented |
| Multiple/default/non-type/template-template parameters and packs | **Rejected** | Only one `typename` or `class` parameter recognized |
| Templated arrays, groups, nodegroups, explicit mainchares or messages | **Rejected / not lowered** | This phase only implements scalar `chare` templates; templated `chare Main` is rejected to preserve the implicit-mainchare convention |
| Cross-file/whole-program auto-discovery | **Not implemented** | Each CLI invocation analyzes one `.csh` unit; consumer-only proxy uses are invisible |
| General header dependency graph and multi-module build | **Not implemented** | Generated header assumes template definition is self-contained; arbitrary source-local dependencies or external interface imports are unresolved |

## Generated artifacts and ordering

For an input module named `Example`, Charm# emits:

1. `Example.ci`: templated `chare` declarations and import of the optional
   specialization module.
2. `Example_specializations.ci` (when needed): concrete runtime registrations,
   explicitly requested or inferred; the primary and specialization modules
   reference each other using Charm++ module declarations.
3. `Example_templates.h` (when templates exist): complete rewritten class
   templates deriving from `CBase_Name<T>`, followed by
   `#define CK_TEMPLATES_ONLY` / `#include "Example.def.h"` /
   `#undef CK_TEMPLATES_ONLY`. It includes `Example.decl.h`.
4. `Example.cpp`: ordinary source-range-rewritten C++ with one include of
   `Example_templates.h`, and conventional module-level `.def.h` includes.
5. `Example.decl.h`, `Example.def.h`, and matching specialization headers
   are generated by **Charm++**, not by Charm#.

Header ordering is intentional: the generated template code needs complete
class definitions before `CK_TEMPLATES_ONLY` exposes the generated template
methods. A separate consumer includes the shared header; there is no separate
`specializations.h`.

or all combinations with other Charm# constructs.

## Implicit-mainchare interaction (follow-up)

A declaration spelled `template<typename T> chare Main` is now rejected
with a source-located diagnostic. The implicit `chare Main` convention applies
to non-template scalar chares only; Charm# does not offer templated mainchares.
Negative parser tests cover both `typename` and `class` spellings, while
positive tests preserve ordinary `chare Main` and `Worker<T>` behavior.

## Known limitations and follow-up priorities

1. **P0 — correct documentation and diagnostics (completed):** Preserve the
   tested/rejected/unverified distinctions; avoid stating that explicit
   registrations validate arbitrary template arguments. The templated
   `chare Main` collision now has a source diagnostic and regression tests.
2. **P1 — shared-header dependency resolution:** For template classes that use
   separately declared bases, helper classes, aliases, or out-of-line method
   definitions, specify which declarations are visible to every consumer and
   emit/import headers accordingly. Do not simply duplicate source-local C++
   definitions across translation units.
3. **P1 — explicit-registration conformance:** Test user-defined and nested
   arguments against the pinned Charmxi parser and Charm++ marshalling/PUP
   behavior, then tighten diagnostics where they fail.
4. **P2 — coordinated multi-file analysis:** Discover `CProxy_Name<Concrete>`
   usages in separate files, deduplicate at module scope, and provide an
   explicit build/registration ownership model.
5. **P2 — template inheritance:** Validate C++ base ordering and generated
   `.ci` inheritance for ordinary and parallel template bases independently;
   the present diagnostic is deliberate.
6. **P3 — broader C++ template surface:** Additional template parameters,
   defaults, partial specializations, other parallel kinds, and general
   dependency/type-resolution support are outside the lightweight v0.1 target.

## Conclusion

Close **Phase 6.3** as **complete for the minimal, documented subset**.
This phase does not make Charm# a general C++ template frontend. The next
development choice should be driven by a real application/benchmark requiring
one of the deferred capabilities rather than by syntactic parity alone.
